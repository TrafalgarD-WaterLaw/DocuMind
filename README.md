## 核心功能

- 💬 **快速问答** — 六路混合检索 + 证据锚定生成,回答携带 `[1][2]` 引用徽章,点击直达证据原文,图文并排对照(如「妇好墓玉龙是什么时期的玉器?」→ 商代、玉器、尺寸、出土信息带引用)
- 🔍 **深度研究** — 史官 / 工艺 / 关联三专家**并行**分析,著述 Agent 融合出带思维导图的综合研究报告
- 📷 **拍照识物** — 上传文物照片,CLIP 图-图余弦在 9468 张图索引上零样本识别(无需训练),置信度门控防幻觉,识别-检索一体
- 🕸 **知识图谱** — 2601 件文物 / 409 遗址 / 11 朝代 / 4 窑口的 Neo4j 图谱,ECharts 交互式展开,图谱问答模板化查询
- 📄 **文档入库** — 上传 PDF 异步解析入库(结构感知切分 + 图片抽取 + VLM 图注),秒级可检索,支持替换重传
- 📊 **全链路可观测** — 每次检索六路命中数与耗时实时流式推送诊断面板,jsonl 落盘可回溯

## 它解决什么问题

**1. 长尾文物知识,通用 RAG 召回差。** 文物是典型的"长尾领域"——同一个器物,用户会问年代、纹饰、工艺、出土、馆藏、文化意义,泛化问答模型对这类冷门实体经常答非所问、甚至编造。难点在于:知识分散在爬取文本、结构化字段、图片图注、图谱关系四种形态里,单一检索路无法覆盖。**所以**做六路混合召回 + 加权 RRF 融合,让每一形态的知识都有独立通道被捞起,再统一融合排序。

**2. 图文分离,"看图说话"弱。** 文物问题天然要看图(器型、纹饰、釉色),但传统 RAG 只索引文本。难点:图片没有自然语言内容,如何进检索?**所以**引入 CLIP 图文同空间编码——图片块(图注级)与文本块同库共存参与融合,CLIP 图找图零样本识别,文找图作为独立检索路;图片证据链随回答返回,图文对照。

**3. 用户问法与库内陈述句的语义鸿沟。** 库内是"妇好墓玉龙,商代,玉器,长7厘米…"的陈述句,用户问"这是什么时期的?"——embedding 距离远,BM25 靠关键词偶合。难点:查询侧增强(如 HyDE)增加延迟与成本。**所以**在**入库侧**为每个 chunk 预生成 3 条假设问题,构建 16152 条问题索引,Q-to-Q 匹配,查询侧零额外延迟。

## 核心设计决策

### 链路 1 · 文档入库:结构感知解析与切片

**难点**:PDF 是"非结构化容器"——表格的语义藏在行列关系里、图片的信息在像素里、多栏排版会打乱阅读顺序、扫描件根本没有文本层。粗暴按字符数硬切,表格被拆碎、图片信息直接丢失,检索时"这件器物的尺寸表在哪""这张图属于哪件器物"无从谈起。

**方案**:按信息类型分流提取,再**以结构为边界切片**:

- **文本(段落/标题)** → Docling 解析为结构化块,标题作为切块边界;
- **表格** → 独立块整体入库(文物图录里的尺寸/形制表,行列关系不拆碎);
- **图片** → 抽图 + 页内"图N"图注配对(同页同序号)+ VLM 描述(无 key 降级为文件名占位)→ 独立图片块,带页码与图号。

**切块策略的关键**:文物文档(图录/鉴赏文)天然高度结构化——一个器物条目 = 标题 + 简介 + 鉴赏分节 + 图片及图注。因此**按结构切而不是按字符数切**:标题、段落、表格各自成为独立**子块**(粒度细、命中准);同一器物的全部子块再拼接成一个**父块**(上限 1500 字,承载完整条目上下文)。命中子块时在同配额内替换为父块——送 LLM 的上下文有硬预算(8 块 × 1500 字 ≈ 8-9k token 封顶),父块补的是语境而非长度;而过滤与引用定位仍基于子块——既保住"精确到段"的粒度,又不丢"整条器物"的语境。

**切片只是入库的一半——同一管道里还完成检索侧的配套工作**:

- **实体抽取**:LLM 从整篇文档提取 ≤5 个实体名(器物/人名/遗址),注入每个块的 metadata——检索时 `entity` 路按实体数组精确匹配,补偿短条目 embedding 劣势;
- **假设问题生成**:为每个块生成 3 条用户可能问的问题,写入独立问题索引(链路 4 的 Q-to-Q 数据来源);
- **索引联动**:BM25 脏标记(下次检索自动重建)、图片映射表更新、指纹记录——上传完成即全链路可检索。

顺带:sha256 指纹去重(重复上传直接跳过);解析失败机器可读分类(加密/权限/超时/无效 PDF/其他),前端直接映射展示,不让用户猜。

**效果**:一次上传 = 文本/图片块 + 实体 + 问题索引 + 映射表全部就绪;命中粒度细(精确到段/图)、上下文完整(父块兜底)、重复上传零重复块、失败有明确分类。

### 链路 2 · 查询理解:改写 → 意图路由 → CRAG 评估闭环

**难点**:用户问法口语化("它是什么时期的?"),复合问句常见("是什么时期,有什么特点?"),而且检索质量在召回前无法预知——答错不如不答。

**方案**:LLM 改写消解代词 → 意图路由(文本/图谱分派)→ 复合问题拆解为子查询;检索后 **CRAG 评估**:LLM 判断证据是否足够,不足 → 改写重检索一轮 → 仍不足 → **拒答**(不编造)。

**效果**:复合问题分而治之、代词指代可追溯;空检索/弱检索走明确拒答路径,演示时"知识库未覆盖"是有据可查的判定,不是幻觉。

### 链路 3 · 六路召回:四种知识形态各有一条通道

**难点**:同一件文物的知识分散在**爬取文本 / 结构化字段 / 图片图注 / 图谱关系**四种形态里,单路检索只能覆盖一部分——"出土于哪"在文本里,"出土地"在图谱关系里,"长什么样"在图片里。

**方案**:并行召回,四条主力通道各司其职,两条辅助兜底:

- `semantic` **向量语义检索** — BGE 编码 9600+ 文本/图片块;配**树状层级剪枝**(窑口→器物→鉴定维度逐层粗筛,候选池逐层收窄,省掉全库扫描)
- `question` **Q-to-Q 问题索引匹配** — 16152 条假设问题独立索引,按"问题形态"直接匹配(见链路 4)
- `graph` **图谱锚定** — LLM 从问题提实体 → Neo4j 查关联(2601 件文物 / 409 遗址 / 11 朝代 / 4 窑口,2803 条出土关系)→ 扩展词补检索
- `clip` **文找图 / 图找图** — CLIP 图文同空间,9079 张图索引:文找图(文本 query 按视觉相似召回,低权重防挤占,见链路 5);图找图(vision 专用通道——上传照片按图-图余弦识别出库内相似文物,识别名再驱动检索,见演示·拍照识物)
- **辅助兜底** — BM25 关键词(jieba 分词,5786 篇)与实体名精确匹配(入库注入的实体数组)各补一路:前者兜关键词偶合,后者补偿短条目 embedding 劣势

**效果**:主力通道覆盖"文本 / 字段 / 图注 / 图谱"四态知识,兜底路补漏;诊断面板实时展示各路命中数与耗时,哪路捞到证据一目了然。

### 链路 4 · 假设性问题索引:把"问法鸿沟"解决在入库侧

**难点**:库内是陈述句("妇好墓玉龙,商代,玉器,长7厘米…"),用户问的是问句("这是什么时期的?")——embedding 距离远,BM25 靠关键词偶合,召回不稳定。

**方案**:入库时 LLM 为每个 chunk 生成 3 条用户可能问的问题,构建独立问题向量索引(16152 条),检索走 Q-to-Q 匹配。

**权衡**:与查询侧增强(HyDE)对比,HyDE 有更根本的问题——RAG 的初衷正是解决 LLM **不具备**的专有领域长尾知识,而 HyDE 让 LLM 先"生成一个假设答案"再去查库:对长尾知识,LLM 猜的答案本身就不准,用不准的答案去匹配,等于拿错的钥匙开锁,陷入"不知道 → 猜 → 猜错 → 查不准"的循环。我们反其道而行:**入库时对着真实答案生成问题**(答案是库内原文,问题由 LLM 从答案反推),问法-答案天然对齐。代价是入库阶段多一次 LLM 调用(资源占用集中在上传,一次性付清),查询侧零额外开销。

**效果**:question 路成为稳定召回来源(每轮 3-6 条命中),且对通用问题形态的加权结论同样来自实验(权重 1.0,不特殊加权)。

### 链路 5 · 融合排序:加权 RRF + 权重实验定标

**难点**:各路召回的"质量"天然不对等——图谱扩展词与语义路**高度重叠**(同一信息被两路同时捞到,RRF 会重复计票);CLIP"视觉相似"常不等于"语义相关"(汝窑天青釉与钧窑天兰釉连人眼都难分,按相似度召回的多是视觉近邻而非答案来源);图注块的语义相似度偏高,会挤占文本证据。

**方案**:加权 RRF(k=60)融合——各路按**排名**投票(排名越前票值越高),天然抑制单路长尾噪声;但统一投票会高估"重叠路"与"噪声路",因此给每路乘路径系数,系数用网格实验定标:

- `graph` 降权 0.5 — 与 semantic 重叠,避免同源信息双计;
- `clip` 压到 0.1 — 视觉相似 ≠ 语义相关,防挤占文本证据;
- 图注块 0.3 — 文本证据弱时可浮上,但不与文本同权竞争。

**效果**:单路噪声被排名机制天然抑制,重叠路不双计,视觉噪声路无法靠相似度堆票上位——每个系数都有实验出处,不是拍脑袋。

### 链路 6 · 上下文净化:块级噪声过滤

**难点**:融合结果不是"全有用"——弱证据块(仅单路低分命中)混在高置信块里送进 LLM,会稀释上下文,让回答抓到噪声而非答案。

**方案**:块级噪声过滤。RRF 分数分布天然分两簇:多路投票的块分数累加后显著偏高(≥0.0308),单路票的块分数偏低(≤0.0167),簇间有明显空隙——取中间值 **0.025 作阈值**,低于阈值且单票、且排名靠后(>4)的弱块直接裁剪,不送 LLM。三条件缺一不可:高阈值但多路票的块保留(多方印证),低分但排名靠前的块保留(该路强信号)。

**效果**:实测约半数弱块被裁,送 LLM 的上下文收窄到高置信证据;过滤基于子块(引用定位仍精确到段),与链路 1 的父子分块设计自然衔接。

### 链路 7 · 生成:证据锚定 + 引用溯源

**难点**:LLM 幻觉引用是 RAG 最大的信任问题;深度研究里多专家转述还会导致引用编号失真。

**方案**:证据块**全局编号 1..N 锚定原文**,著述 Agent 直接引用原始证据块(而非专家转述);生成提示词强制"只标实际提取自该编号的信息,否则注明(补充)";多模态问答把**识别名作为强约束**注入 prompt("照片已识别为「妇好墓玉龙」,只围绕它回答")。

**效果**:回答中 `[1][2]` 徽章点击直达证据原文,图文对照;报告引用与证据一一对应,可审计。

### 工程底座 · 外部依赖结构化降级

**难点**:Neo4j 是外部依赖——宕机时问答链路不能断;重模型加载会阻塞首问。

**方案**:图谱查询**模板化 Cypher(T1-T6,不自由生成)**防注入;Neo4j 连接失败进入 60s 冷却期快速失败并**静默降级文本检索**;BM25/CLIP/embedder 启动**后台预热**,请求零等待。

**效果**:实测图谱完全宕机时检索契约仍 28/28 全绿;首问不被 1 分钟级模型加载阻塞(启动后即问即答)。

## 系统架构

```
用户问题
   │
   ▼
查询理解 ── 改写(代词消解) → 意图路由 → CRAG 质量评估 → 实体锚定
   │
   ▼
六路混合召回 ────────────────────────────────────────────────┐
  semantic  向量检索(树状层级剪枝:窑口→器物→鉴定维度)        │
  question  假设性问题索引 Q-to-Q(16152 条,入库侧预生成)     │
  bm25      jieba 分词关键词匹配                              │
  graph     Neo4j 图谱锚定(LLM 提实体 → 扩展词补检索)         │
  entity    文本实体名精确匹配(短条目 embedding 劣势补偿)     │
  clip      CLIP 文找图(图-文同空间余弦,低权重防挤占)         │
   │
   ▼
加权 RRF 融合(k=60,路径权重网格实验定标)→ 块级噪声过滤 → 证据链
   │
   ▼
证据锚定生成 ── 全局编号引用溯源 → 流式回答(NDJSON:思维链/内容/来源/轨迹)
```

## 快速开始

### 1. 启动后端(端口 5172)

```bash
cd backend
cp .env.example .env          # 必填 DEEPSEEK_API_KEY;Neo4j/百炼可选,缺省自动降级
uv sync
uv run python src/main.py
```

启动后看到 `════ 全部加载完成,可以开始提问 ════` 即可提问(约 1.5 分钟预热)。

本地模型(BGE / CLIP / reranker)从 ModelScope 缓存加载,默认路径见 `backend/src/core/config.py`,可用环境变量覆盖。

### 2. 启动前端(端口 5173)

```bash
cd frontend
pnpm install
pnpm dev
```

浏览器访问 `http://localhost:5173`。

### 3. 可选:Neo4j 知识图谱

未启动时图谱问答与图谱探索不可用,其余功能不受影响。
