## 一、架构治理（前置地基）

> 数据契约统一是后续所有优化的载体。检索核心不动（评测基线保护）。

| 项 | 内容 |
|---|---|
| P1-A | `chunk_type` 全量标记（文本补 `text`）+ 迁移脚本（只改 metadata 不重 embedding） |
| P1-B | `image_path` 统一带 `/api/` 前缀 + 前端删裸相对分支 |
| P1-C | source 命名规范文档化 + ingest 管道校验（不重命名存量） |
| P1-D | 清理测试残留（3 旧版本 chunks + 3 废 PDF） |
| P2 | 统一 ingest 管道（BaseIngestor + 注册表；旧 7 脚本标 deprecated 不重写） |

## 二、切片优化（⭐⭐⭐）

**现状分析**：`RecursiveCharacterTextSplitter` 固定 500 字符 + 50 重叠，纯字符级切分——Docling 解析出的结构信息（blocks: type/page/bbox）被丢弃（upload.py 把 parsed.markdown 打散重切）。

**业界方案**：结构感知切分（RAGFlow DeepDoc 标配）、父子分块（Small-to-Big，LlamaIndex 标配）、语义切分、LLM 切分。

**优化方案**：
1. **结构感知切分**：直接用 Docling blocks 切——段落为主块、表格独立块、标题引导块；不跨结构切。成本半天。
2. **父子分块**：小块 200-300 检索 + 父块 500 送 LLM（metadata 记 parent_id）。已有雏形：question 路 = 假设问题小块 → `source_chunk_id` 映射回原文大块。成本半天。
3. **验证**：改造前后跑 eval 核心集 + 扩展集，Recall/MRR 量化收益。

## 三、向量化（可选 ⭐⭐）

**现状**：bge-small-zh-v1.5（512 维）本地离线。

**业界路径**：bge-m3（稠密+稀疏+多向量一体，8192 token）、gte-Qwen2（中文 SOTA）、领域微调（简历项目不值）。

**优化方案**：bge-m3 升级评估——全库重 embedding（9359 + 16507 条，本地几分钟）+ 评测对比；收益明确才切换。**附带收益**：稀疏向量可替代独立 BM25 路（一路变一体，简化五路架构）。

## 四、查询理解（已达标，可选增强）

**现状（✅）**：
- 查询改写：LLM 代词消解（多轮"它属于什么朝代"→"妇好鸮尊属于什么朝代"），失败回退拼接
- 意图路由：FEATURE_WORDS 拦截（特点/纹饰/演变）→ 文本检索；REL_WORDS → 图谱结构化；实体名匹配 → 图谱
- CRAG：检索质量评估（good/poor）→ poor 改写重检索一轮
- 实体锚定：LLM 提实体 + 规则回退 + 图谱校验

**业界可选增强**：
- **HyDE**：LLM 生成假设答案 → 用答案检索（查询-文档分布对齐）。适合查询词与文档表述差异大的场景；我们已有 Q-to-Q 假设问题索引（同类思想，收益重叠）→ **不做**
- **查询分解**（sub-question）：复杂多跳问题拆子查询分别检索再合并。**已完成（2026-08-08）**：复合问题（多实体/比较/联合）LLM 拆 2-3 子查询 → 各自五路检索 → 合并证据；非复合零成本（判定保守回退）。实测："妇好鸮尊和司母戊鼎哪个更早"从司母戊鼎 0 证据 → 两实体证据齐全；单实体查询判定不误伤

## 五、重排（已实验否定，维持禁用 ✅）

**实验（2026-08-08，eval/rerank_grid.py，核心集 28 题；CPU + GPU 两轮）**：

| 配置 | Recall@8 | MRR | 路径覆盖 | 耗时/题 |
|---|---|---|---|---|
| off（现状 RRF） | **100%** | **0.7173** | 81.8% | 2.7s（CPU） |
| on-p16-c32（GPU） | 92.9% | 0.6173 | 77.3% | 35.6s |
| on-p32-c128（CPU） | 92.9% | 0.6173 | 77.3% | 44s |

**结论：cross-encoder 全面退化（Recall -7.1pp / MRR -14%）**，维持 `use_rerank=False`。
**CPU/GPU 两轮数字完全一致**——退化与硬件/候选池/耗时无关，是打分本身的系统性偏差。

**为什么退化（面试必答）**：
1. **多路融合信息丢失**：RRF 的五路票（semantic/question/bm25/entity/graph）是强信号——cross-encoder 只对 (query, doc) 单对打分，question 路的 Q-to-Q 强映射、entity 路的器名精确匹配都被抹平
2. **块形态干扰**：短标题块/单票块被重排器排前，长文段强相关块被挤后（文物块长 500-1500 字，与重排器训练分布不匹配）
3. **成本不可用**：CPU 上 44s/题（16 倍），生产不可行

**历史闭环**：旧配置（top-8 内微排序）启用无增益 → 本轮大候选池（128）反而显著退化——**rerank 被用数据彻底否定**（不是没试过）。若未来换 GPU 或换领域重排模型可重跑本网格（脚本保留 eval/rerank_grid.py）。

## 六、上下文组装（❌ 待优化 ⭐⭐⭐）

**现状分析**：top-8 直接全塞 LLM（每个 400 字截断）——**不过滤噪声块**。噪声稀释注意力、增加幻觉、浪费 token。CRAG 只做**整体**评估（不够→重检索），块级过滤是下一层。

**业界方案**：Context Compression（LlamaIndex）、相关性阈值过滤、LLM 判断过滤（RAGFlow）。

**优化方案**（轻量版，半天）：
1. **分数阈值过滤**：RRF 融合分低于阈值的块丢弃（或保留 top-4 强相关块 + 阈值裁剪）
2. 可选进阶：LLM 逐块判断（准确但贵，后置）
3. 与 CRAG 互补：CRAG 管"整体不够"，块级过滤管"块内噪声"
4. 验证：judge 评测（faithfulness 提升 = 噪声过滤有效）

## 七、评估体系（⭐ 补维度 ⭐⭐⭐）

**现状**：Recall（检索召回 100%）、MRR（排序 0.71/0.97）、judge（LLM 判 GT 事实，85%）。

**业界 RAGAS 四维**：
- **faithfulness 忠实度**：回答每个事实是否被检索上下文支持（幻觉度量）——**我们缺的维度**
- answer relevance：回答切题度
- context precision/recall：上下文质量

**优化方案**（半天）：judge 脚本加 faithfulness 维度（LLM 逐句判"是否被上下文支持"）→ 幻觉可量化 → 面试讲"我怎么度量幻觉"。

## 八、多轮记忆（❌ 待优化 ⭐⭐）

**现状**：`_with_history` 硬截断最近 6 轮 × 200 字。

**业界方案**：消息摘要压缩（旧轮次 LLM 摘要成概要，替代硬截断）、对话状态跟踪。

**优化方案**（1 天）：历史摘要化——超过 N 轮后，旧轮次压缩为一段摘要进上下文，保留近期完整轮次。长对话"忘事"问题的正解。

## 九、缓存（⭐ 低优先，暂不做）

语义缓存（相同/相似问题缓存答案）省 token 降延迟——演示价值低，业界主要为了省钱。**不做**。

## 十、实施顺序（整合）

```
第 1 步：架构治理 P1 → P3          （1-2 天）数据契约是优化载体
第 2 步：切片优化 + 上下文过滤      （1-1.5 天）并行做，共用 ingest 管道
         └─ 改造前后 eval + judge 对比（含新增 faithfulness 维度）
第 3 步：重排正确接入实验           （1 天）候选池网格 + 评测决定
第 4 步：多轮记忆摘要压缩           （1 天）
第 5 步（可选）：bge-m3 评估、查询分解
随时可插：DashScope key → 图片块 VLM 描述
```

**原则**：每一步改造都有评测基线保护（eval 核心集/扩展集 + judge），用数字说话——这是"有工程意识的 RAG 优化"叙事。

## 十一、明确不做

- 存储换库（Chroma 规模远未到瓶颈）
- embedding 领域微调（成本不值）
- HyDE（与 Q-to-Q 问题索引收益重叠）
- 语义缓存（演示价值低）
- 多知识库/权限体系、MinerU 接入
