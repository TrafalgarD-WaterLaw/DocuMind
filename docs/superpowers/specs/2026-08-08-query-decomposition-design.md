# 查询分解设计（复合问题子查询检索）

日期：2026-08-08
参考：docs/rag-optimization-blueprint.md「四、查询理解 可选增强」

## 一、现状问题（实测实证，2026-08-08）

| 查询 | 结果 |
|---|---|
| 妇好鸮尊和司母戊鼎哪个更早 | **6 个 sources 全为妇好鸮尊，司母戊鼎 0 证据**——回答中"司母戊鼎也是商代晚期"为 LLM 编造（无证据幻觉） |
| 叩鼎和素面弦纹鼎分别出土于哪里 | 图谱结构化路只处理素面弦纹鼎（叩鼎未入查询），回答质量差 |

**根因**：单查询单路检索——多实体/比较问题只召回一个实体，另一实体无证据 → LLM 常识补全 = faithfulness 违规。

## 二、方案：LLM 判定 + 子查询检索 + 合并

```
quick_answer 前端（意图分析前）:
  LLM 判定复合？（多实体/比较/联合条件）
    ├─ 否（或失败）→ 原链路（零变化，单实体问题零成本）
    └─ 是 → 拆 2-3 子查询
             → 每子查询: 改写 + 五路混合检索（含 graph 锚定，跳过图谱结构化路由）
             → 合并证据（去重 by id，保持子查询顺序）→ 编号引用组装回答
```

**组件**：
1. `prompts/query_decomposition.md`：判定 + 拆解（输出 JSON 数组或原样文本；保守——单实体问题必须原样返回）
2. `services/query_decomposition.py`：
   - `decompose(query, llm) -> list[str] | None`——复合 → 子查询列表；非复合/解析失败/LLM 异常 → None（回退原链路，零成本）
   - 判定规则（防误伤）：子查询数量 ≤3；每个子查询非空且含实体词
3. `orchestrator.quick_answer` 接入：
   - 分解成功 → 循环子查询（复用现有"改写 + retriever.retrieve"路径，use_graph 默认开；不做 CRAG 重检索，控制成本）→ 合并去重 → doc_context 编号
   - 分解失败/非复合 → 原链路完全不变（含图谱结构化路由）
4. **验证**：
   - 单元测试：判定/拆解/解析失败回退/非复合原样/合并去重
   - 真实复测：两个实测问题（司母戊鼎证据出现 = 成功）；单实体查询回归（判定不误伤，回答/证据与改造前一致）
   - eval --retrieval-only 回归（检索端未动，确认无影响）

## 三、范围

**做**：判定 + 拆解 + 子查询检索合并 + 测试复测。
**不做**：子查询级图谱结构化问答（_structured_answer 不参与分解路——graph 证据经 graph 路锚定进入文本证据，统一合并逻辑）；多轮分解缓存；Least-to-Most 逐步推理。

## 四、验收

1. "妇好鸮尊和司母戊鼎哪个更早"→ sources 同时含两者，回答两实体都有引用证据
2. "叩鼎和素面弦纹鼎分别出土于哪里"→ 两者证据都在
3. 单实体查询（如"叩鼎的纹饰特点"）→ 行为与改造前一致（判定不误伤）
4. 全量 pytest 通过；eval --retrieval-only 无回归
